# 科信小助手 2.3.9

版本码 168 · 2026-11-16

## -3 的真因：支付方式被我们过滤错了

上一版的只读诊断把答案直接摆了出来。`bill/lst-owner` 返回的账单里，这个账户在这台机器上的**每一笔成功消费都是 `type: 21`**：

```json
{ "payment": 0.14, "status": 3, "type": 21, "dir": 1, "msg": "水控/直饮机设备(成学楼4楼热水)消费" }
```

4 笔，金额 0.14–0.21 元，全部 `status: 3`（已完成）。也就是说这台机器日常走的支付方式就是 21——元级小额直扣，按账单和官方包里的支付宝生态（授权登录、碰一碰红包），是**支付宝免密代扣**。

而我们此前只认官方 3.1.5 `PaymentType` 枚举里的 91 商家钱包、92 余额。服务端 `payItems` 给的 `[{seq:100,type:91},{seq:90,type:21}]` 中，21 被当成「未知方式」过滤掉，页面只剩**商家钱包**——`wallet.total` 为 0 的那一个。用它开启，服务端回 `-3`。四个版本里反复撞的那堵墙，是自己砌的。

顺带定下来的其它事实：

- `dev-use-way` 需要额外参数（带 `did` 回 `-1 请求参数错误`），暂时用不上；
- `dev/status` 确认 `gene = {mode:0, out:73987.572, status:99, err:0, vel:0}`：流速 0、无错误，`status 99` 在这台水控机上就是空闲待用。

## 改了什么

- **`21` 正式收下**：服务端给的支付方式里，21（支付宝免密）、91（商家钱包）、92（余额）、93（一卡通）都可选，未知编码仍然拒收（看不懂的扣费通道不能乱选）。
- **默认选中的是账单在用的那一种**：按 `seq` 降序排（这台机器 91→100、21→90），但商家钱包余额为 0 时自动挪到最后——余额 0 的方式排第一只会让人点一次就被 `-3` 打回来。
- **失败提示直接给行动**：选了商家钱包被拒时，写明「换支付宝免密再试」。
- 确认框说明「排在前面的是账单里一直在用的那种」。
