# 科信小助手 2.3.5

2026-11-16。「请升级最新版APP」终于对上了号：不是参数错，是版本号太低。

## 结论

2.3.4 里加的「复制诊断信息」把关键信息交了出来：同一份文件里设备详情是成功的，设备名、位置、计费方式、余额全都正常，只有开启请求被同一句话挡回。也就是说：

- **凭据没问题**；
- **设备标识没问题**；
- **参数也没问题**——这次服务端给的不是「请求参数错误」，而是「请升级最新版APP」。

差别在版本头。本项目此前按官方旧版本对齐，而服务端对这条控制请求设了最低版本要求，旧版本正好在门槛之外，所以在跑业务逻辑之前就把请求退回来了。这也解释了为什么详情请求（没有版本门槛）能用、开启不能，以及为什么同一个失败码的说明文字会变。

## 改了什么

**版本号按官方现役对齐**（`LifeVersion`）：控制类请求改发与服务端要求相符的版本头。另外留了一条保底阶梯——万一服务端再抬门槛、回的还是「请升级」，就按预设序列往上试，**第一个不被拦的版本号会被记住**，下次直接用。只在服务端明确要求升级时才重试：那句话意味着请求没进业务逻辑、水没开，重发不会多开一次水；「过期」「参数错」这类一律不重试。

**「核实并归档」整套拆掉**（`LifeWaterActivity`）：`LifeWaterRecord` 这个类连同它的读写、撤销、归档逻辑一起删除。它原本的作用是「发请求前先记一笔，防重复开启」，可它记的是「我发过」，不是「服务器收了」——上一次被版本门槛拒掉的那次也记了，于是页面自己把自己锁住，逼用户去核实一笔不存在的账单。现在页面只有两种状态：设备空着就给「开启用水」，本账号正在用就给「结束用水」。

**失败提示分清两种后果**：被服务器明确拒绝 → 「设备状态没有改变，可以重试」；超时、HTTP 错误、解析失败这类 → 「结果未确认，请刷新核实设备状态」。

**诊断信息里加上本次使用的版本头**：下次再看，能直接知道这次是按哪一档版本号请求的。

## 验证

- 核心断言 1034 项通过；fieldtest 断言新增 8 条（版本阶梯起点、升级判定只认「请升级」、记住的版本号排在阶梯最前、页面里不再有 `review` 字段）；
- `aapt2` 读到 `versionCode=163 / 2.3.5`；v2/v3 签名通过；
- APK 内确认含 `LifeVersion`、`life-version-v1`，不再含「核实并归档」；
- 线上清单解析通过：`2.3.5 / 163 / 5338780 bytes / sha256 c935f232…d09e98d`；
- **仍未真机验证**：对齐后的版本头能不能穿过那道门槛，只有装上按一次才知道。

## 装上之后

1. 扫码进用水页，应当直接看到「开启用水」（不会再出现任何「核实/归档」）；
2. 点它 → 选「商家钱包」→ 确认开启。如果这次成了，设备会出水，页面变成「结束用水」；
3. 如果仍失败，把提示发我——现在的提示会带服务端原话，再加 ⓘ 里的「复制诊断信息」（里面已有版本头），能直接判断是门槛更高了还是另有原因。
