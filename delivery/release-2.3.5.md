# 科信小助手 2.3.5

2026-11-16。「请升级最新版APP」终于对上了号：不是参数错，是版本号太低。

## 那份诊断信息说了什么

2.3.4 里加的「复制诊断信息」把这段交了出来：

```json
"sent": "/api/v1/dev/start?did=863781053404316&upgrade=true&ptype=91&args=&rcp=false&cnt=1",
"reply": { "code": -1, "msg": "请升级最新版APP" }
```

同一份文件里的 `detail` 是 `code:0`，设备名、位置、`ep.setting`、`payItems`（`91` 商家钱包、`21` 余额）、`gene.status=99` 全都正常。也就是说：

- **凭据没问题**（详情接口用同一个 token 拿到了完整数据）；
- **`did` 没问题**（详情就是按这个 `did` 查的）；
- **参数也没问题**——`-1` 的 `msg` 这次不是「请求参数错误」，而是**「请升级最新版APP」**。

差别在请求头。我们从官方 3.1.5 抄来的头是 `ApplicationType: 1,1` + `VersionCode: 31005`。官方现役版本是 **3.1.10**，版本号规则是「三位各占一段」——3.1.5 → `31005`、3.1.10 → **`31010`**。服务端对 `/api/v1/dev/start` 这一支按 `VersionCode` 设了最低版本墙，`31005` 正好在墙外，于是它在跑业务逻辑之前就把请求退回来了。这解释了为什么详情接口（没有版本墙）能用、开用水不能，也解释了为什么 `-1` 的 `msg` 会变——`-1` 只是通用的失败码，具体原因全在 `msg` 里。

## 改了什么

**版本号按官方现役对齐**（`LifeVersion`）：控制类请求改发 `VersionCode: 31010`。另外留了一条梯子——万一服务端哪天再抬门槛，回的还是「请升级」，就自动往上试（31020、31100、32000、33000、40000、50000），**第一个不被拦的版本号会被记住**，下次直接用。只在 `msg` 明确说「升级」时才重试：那句话意味着请求没进业务逻辑、水没开，重发不会多开一次水；`-99`（过期）、`-1`（参数错）这类一律不重试。

**「核实并归档」整套拆掉**（`LifeWaterActivity`）：`LifeWaterRecord` 这个类连同它的读写、撤销、归档逻辑一起删除。它原本的作用是「发请求前先记一笔，防重复开启」，可它记的是「我发过」，不是「服务器收了」——上一次被版本墙拒掉的那次也记了，于是页面自己把自己锁住，逼用户去核实一笔不存在的账单。现在页面只有两种状态：设备空着就给「开启用水」，本账号正在用就给「结束用水」。

**失败提示分清两种后果**：被服务器明确拒绝 → 「设备状态没有改变，可以重试」；超时、HTTP 错误、解析失败这类 → 「结果未确认，请刷新核实设备状态」。

**诊断信息里加了 `versionCode`**：下次再看，能直接知道这次是按哪一档版本号请求的。

## 验证

- 核心断言 1034 项通过；fieldtest 断言新增 8 条（梯子起点是 31010、`upgradeRequired` 只认「升级」不认 `-1`/`-99`/`code:0`、记住的版本号排在梯子最前、页面里不再有 `review` 字段）；
- `aapt2` 读到 `versionCode=163 / 2.3.5`；v2/v3 签名通过；
- APK 内确认含 `LifeVersion`、`life-version-v1`，不再含「核实并归档」；
- 线上清单用 `UpdateManifest.parse` 解析通过：`2.3.5 / 163 / 5338780 bytes / sha256 c935f232…d09e98d`；
- **仍未真机验证**：`VersionCode: 31010` 能不能穿过那道墙，只有装上按一次才知道。

## 装上之后

1. 扫码进用水页，应当直接看到「开启用水」（不会再出现任何「核实/归档」）；
2. 点它 → 选「商家钱包」→ 确认开启。如果这次成了，设备会出水，页面变成「结束用水」；
3. 如果仍失败，把那句提示发我——现在的提示会带服务端原话，再加上 ⓘ 里的「复制诊断信息」（里面已有 `versionCode`），能直接判断是墙更高了还是另有原因。
