# CampusKit 1.4.9

2026-11-16。版本代码 144，`delivery/CampusKit-1.4.9.apk`，
sha256 `9661900476b2f7d06314dd4037fed9b490fea597d99ea877fbe8d16e48549e54`。
签名密钥与 1.4.8 相同，可直接覆盖安装；课表、趣智登录状态、慧生活/教务账号都保留。

这一版只做一件事：**慧生活798 扫码**。

## 问题

慧生活更新后，贴纸与设备屏上的码换成了链接形式，`?id=` 后面跟的不再是设备编号，而是一张需要先向服务端兑换的票据。上一版仍按「编号」处理，把票据直接拿去查设备，自然查不到；更早的版本还会因为「编号里必须含数字」把这类码直接判成「不是设备码」。相机识别一直没有问题，错在把票据当成了编号。

## 改了什么

解析结果现在分两类，扫码后按类型选择后续动作：

| 码的样子 | 含义 | 之后怎么做 |
|---|---|---|
| 链接中 `?id=` 带票据（含带 `bm?/` 的变体） | 票据 | 先兑换成设备编号，再查详情 |
| 链接里直接是设备编号 | 设备编号 | 直接查详情 |
| `ilife798s://` 开头的 NFC 标签 | 设备编号 | 直接查详情 |
| 纯数字 / `did=` / `?q=` / `ilife://device/…` / JSON | 设备编号（旧贴纸） | 直接查详情 |

配套三处修正：

1. **票据字符集放宽**，允许 `% + . / = ~ ? -`，最长 300 字符；票据本身带问号和斜杠，发请求前按 unreserved 规则做百分号编码。
2. **不再要求编号含数字**——那是纯设备编号的规则，票据不适用。
3. **兑换返回的类型放宽到设备（3）与门锁（8）**，其余类型在界面上写清「服务器返回类型 N」，不再笼统地说「不是受支持的用水设备码」。

设备页现在能接收两种入参：设备编号直接查，票据先兑换。扫码页按解析结果选择，不再一律走一次兑换。

## 参考

解析规则参考了两个同类开源实现（均为 MIT 许可，且都在持续跟进线上服务）：

- [`ilife798/ilife798`](https://github.com/ilife798/ilife798)：扫码只负责拿到票据，换编号交给独立的兑换步骤；返回类型为 3（设备）或 8（门锁）才算可用。
- [`nocookies111/life-798`](https://github.com/nocookies111/life-798)：同一套 `?id=` 语义的设备编号解析。

本项目按上述语义在 `Life798Qr.Scan` 中自行实现，未复制其代码。

## 验证到哪一步

- 核心断言 **876 项通过**（1.4.8 是 864）。新增覆盖：五种票据链接、`bm?/` 原文保留、NFC 深链、直连编号，以及 `hello` / `about` / 多段路径等拒绝情形。
- 同一个解析器在真实 JVM 上运行，不是模拟。
- `aapt2` 读到 versionCode 144 / versionName 1.4.9，v2/v3 签名校验通过。
- **没做到的**：仍无真机，带登录态的兑换无法离线验证。装上后请再扫一次；若仍失败，页面会显示「识别到的内容」原文和失败阶段（兑换 / 查详情），把那一行发我就能判断是票据没换到还是详情接口变了。

> 注：如果设备上贴的是微信/支付宝「小程序码」（圆形那种），任何二维码解码器都读不了，只能走「手动输入设备编号」。这一版没有改变这一点。
