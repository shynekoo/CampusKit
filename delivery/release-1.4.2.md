# CampusKit 1.4.2

2026-11-15。版本代码 137，`delivery/CampusKit-1.4.2.apk`，4,866,914 字节，
sha256 `6f3bc2b5cf8c64e52587e6e297b795354a03d085d691f532b8ced5e9e37fa32d`。
签名密钥与 1.4.1 相同，可直接覆盖安装；课表、趣智登录状态、设置都保留。

这一版只解决一件事：**点「去支付宝」提示登录失效**。

## 结论：账号没失效，是下单请求少带了一个 `userId`

你说得对，登录确实没失效。原来那句「登录已失效」不是服务器说的，是我们自己把
「下单被拒」当成了「会话过期」写上去的——这是第一个错。

真正的错在下单报文。我对两条充值通道各发了一次假凭据的探测请求：

```
POST v3-api/settlement/alipay/recharge/balance   不带 userId
  → {"errorCode":8,"errorMessage":"未获取到用户信息，请重新登录"}

POST v3-api/settlement/alipay/recharge/balance   带 userId
  → {"errorCode":8,"errorMessage":"登录失效，请重新登录"}
```

同一份报文、同一个假 token，**只差一个 `userId`，错误就从「未获取到用户信息」变成
「登录失效」**。前者是服务端连用户都没找到，后者是找到了用户、只是 token 是假的。
原版 `BaseNetActivity.t0(map, MyApp.e)` 里 `userId` 是**只在迁移过的校园（v3 通道）才加**
的字段，而我上一版没有区分，v3 通道从来没带过它——所以服务端一直答「未获取到用户信息」，
我们把它显示成了「登录已失效」。

## 改了什么

1. **报文按原版 `t0` 一比一对齐**，不再多带、不再少带：

   | 字段 | 旧版钱包通道 | v3 结算通道 |
   | --- | --- | --- |
   | `payWay` / `rechargeMoney` / `signature` | 有 | 有 |
   | `projectId` | 有 | 有 |
   | `accountId` | 有（为 0 时不发） | 有（为 0 时不发） |
   | `userId` | **不发** | **发**（原来是漏的） |
   | `telephone` | 不发 | 发（原来对两条通道都发了） |
   | `telPhone` | 有 | 有 |
   | `loginCode` / `phoneSystem` / `version` | 有 | 有 |

2. **两条通道都试一遍**。校园走哪条通道由服务器给（`UserInfo.isMigrated`），但猜错一次
   代价就是这个功能整块不能用。现在第一条通道拒绝就换另一条再试一次；只有「服务器明确拒绝、
   肯定没建单」的情况才换，网络超时这种「可能已经建单」的情况**绝不重发**，避免重复订单。

3. **失败提示改成说人话**。两条都拒绝时显示：

   > 两条充值通道都没接受这笔订单。支付宝直连通道：错误码 8 未获取到用户信息，请重新登录；
   > 旧版钱包通道：参数错误（错误码 1）。余额刚才是用同一个登录状态查出来的，所以账号没有
   > 失效。把这句话发给我，我按错误码继续对。

   不再把服务端的拒绝伪装成「登录已失效」。

4. **每个请求都带上 `Config-Project` 和 `Config-Keys` 头**。这是原版 `BaseNetActivity.u0()`
   对**每一个**请求都会加的两个头：前者是这次请求说的哪个校区（正文里的 `projectId`），
   后者是固定的一串配置名 `module_list,advertise_type,…,aliCard_popup_config`。
   我们之前一个都没发。实测这两个头不影响登录校验（带不带都是同一个错误），但既然是原版
   的固定行为，就补上。

5. **少一次请求**。原来下单前要额外查一次 `project/info/triple` 才知道走哪条通道；现在
   直接读 `user/info` 里已经拿到的 `isMigrated`，和账号字段来自同一份回包，两者不可能打架。

## 顺手验证到的：签名是对的

给旧版钱包通道发 `/wallet/recharge/aliPay`，用我们自己算的签名 + 假 token：

```
signature=x（乱填）      → {"errorCode":1,"message":"参数错误"}
signature=51edfe9817…（自算） → {"errorCode":8,"message":"登录失效,请重新登录"}
```

错误从「参数错误」前进到「登录失效」，说明**签名算法（字段名排序拼值 + `sign-kailu=` + MD5）
被服务器接受了**，只是 token 是假的。这条向量已经写成断言，签名一旦漂移测试立刻红。

## 验证到哪一步

- 核心断言 **774 项通过**（1.4.1 是 763；新增 11 项：`projectId` 只能整字段取值
  ——`myprojectId=9`、`projectId=9a`、`telephone=projectId%3D9` 都不得当成校区、
  以及上面那条被服务器接受过的签名向量）。
- 对两条真实接口做了**未登录探测**，确认：两条通道都在线；v3 通道有/无 `userId`
  给出不同错误；自算签名能过参数校验。这些是本次判断的全部依据。
- `aapt2` 读到 versionCode 137 / versionName 1.4.2，v2/v3 签名校验通过。
- **没做到的**：仍然没有设备（adb 无设备，MuMu 起不来），所以「真账号下一单能不能成」
  没有实测。上面的探测只能证明报文形状对了、签名过了、`userId` 是那句话的分水岭。

如果这一版还不行，提示会明确写「两条充值通道都没接受这笔订单」并带上两边的错误码，
把那句话发我就能直接定位到是哪一环。
