# 科信小助手 2.3.4

2026-11-16。扫码进用水页后被自己挡住的那条记录，和一句没头没尾的「业务码 -1」。

## 用户看到的两屏

1. 扫码进「慧生活 · 用水」，设备名、位置都对，但没有「开启用水」，只有一行「设备已无使用者，请核实停水与账单后完成。」和一个「核实账单并完成」；
2. 再点一次刷新，按钮出来了，按下去是「服务器拒绝请求（业务码 -1）。操作记录已保留，请刷新核实，不会自动重发。」

两屏其实是同一件事的两头。

## 分析

**第二屏**：`-1` 还是那个通用「请求参数错误」。同一台设备的详情请求（`/api/v1/ui/app/dev/home/1?did=&apply=6`）是成功的——名字、位置都显示出来了——所以凭据和 `did` 都没问题，是 `/api/v1/dev/start` 这一支的参数不对。这一点**没法从外部探出来**：这条路由先校验凭据再校验参数，没有真 token 只会拿到 `-99`，只有装机才能看到 `-1`。参数表来自官方 3.1.5（`did`、`upgrade`、`ptype`、`args`、`rcp`、`cnt`，见 `analysis/life798-independent-flow.md`），其中 `args` 是「随设备模式变化」的那个，`ptype` 是付款方式——两个都可能是原因，本版不猜。

**第一屏**：2.3.2/2.3.3 在发请求**之前**就写下「待核实记录」，而那次请求被拒了、设备什么都没发生。记录留着不走，后果就是每次进页面都判定「上一笔还没有核实」，于是藏掉「开启用水」，逼你去核实一笔根本不存在的账单。**这不是服务器状态，是本机自己卡住了自己。**

## 改了什么

**撤销被拒的记录**（`LifeWaterRecord.discard`）：只有「服务器明确拒绝且业务码是 -1」才撤销——`-1` 表示参数没通过校验，请求连业务逻辑都没走到，设备状态不可能变。别的负数码、超时、HTTP 错误一概保留记录，那正是记录存在的意义。撤销后弹一句 Toast 说明并把页面刷新回正常状态，不再停在灰按钮上。

**失败信息带上服务端原话**：`LifeDeviceFailure.success` 现在把 `msg` 一起接进去，显示成「服务器拒绝请求（业务码 -1：请求参数错误）」。同时新增 `Rejected` 子类，让上层能区分「明确拒绝」和「结果未知」。

**旧记录不再无路可走**：页面提示改成「上次开启没有完成：设备现在无人使用。确认没有产生账单后归档这条记录，就能重新开启。」按钮从「核实账单并完成」改成「核实并归档」——它本来就是那个动作，原来的字让人不敢按。

**诊断入口**：设备详情（右上角 ⓘ）多了「复制诊断信息」，把这台设备的**原始返回**、这次请求的路径和服务器原文复制到剪贴板，账号、token、手机号、uid 一类字段在复制前就被剔掉（`scrub`）。下次要修 `-1`，靠的就是这份东西。

## 验证

- 核心断言 1034 项通过；新增 fieldtest 断言：`discard` 之后记录为空、`Rejected` 带上业务码与服务端原话；
- 构建通过，`aapt2` 读到 `versionCode=162 / 2.3.4`；
- APK 内确认含 `复制诊断信息`、`记录已撤销`、`Rejected`；
- 线上清单用 `UpdateManifest.parse` 解析通过：`2.3.4 / 162 / 5338780 bytes / sha256 ad03474e…b5557`；
- **`开启用水` 仍未成功**：本版只把页面解卡，`-1` 的成因要等那份诊断信息。

## 装上之后按这个顺序做

1. 进用水页（扫码或从记录进入）。如果还显示「上次开启没有完成」，点「核实并归档」→ 弹窗「已核实，归档」→ 页面回到「设备已就绪」；
2. 点「开启用水」。若仍是 `-1`，现在会自动撤销记录并弹一句原因，页面刷新回可再试的状态，不会再把页面锁死；
3. 点右上角 ⓘ → **「复制诊断信息」**，把复制到的内容发我。里面是这台设备的 `ep.setting`、`payItems`、`gene` 等原始字段——官方客户端就是拿这些拼请求的，有了它就不用再猜 `args` 和 `ptype`。
